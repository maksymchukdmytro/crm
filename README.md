# CRM для товарного бізнесу

Власна CRM для продажів з лендингів: прийом заявок, обробка менеджерами, склад і закупівлі,
ТТН Нової Пошти / Укрпошти / Meest, трекінг, накладені платежі зі звіркою, SMS/Viber та аналітика
апруву й викупу за джерелами трафіку.

**Інтерфейс** — окремий застосунок на React поверх JSON API: список на тисячі рядків без гальм,
картка замовлення поверх списку, канбан-дошка з перетягуванням, пошук Ctrl+K і оновлення в реальному
часі (зміни колег видно одразу). Класичний серверний інтерфейс лишається запасним за адресою `/classic`.

## Архітектура

```
Браузер ── React-застосунок (frontend/, Vite + TypeScript)
   │  JSON API /api/*  ·  події /api/events (SSE)
   ▼
FastAPI (app/) ── PostgreSQL (дані)
   │      └────── Redis ── черга задач arq ── worker.py (SMS, ТТН, трекінг)
   │                    └─ канал подій crm:events → SSE у браузер
   └ класичний HTML-інтерфейс /classic (Jinja2) — запасний
```

- **Черга задач (arq + Redis).** SMS ставляться в чергу після коміту й відправляються воркером з
  повторними спробами; масове створення ТТН виконується у фоні; трекінг запускається кожні 5 хв
  окремою задачею для кожного перевізника, тож один повільний API не гальмує інших.
- **Події в реальному часі.** Будь-яка зміна замовлення чи товару (з інтерфейсу, API, webhook або
  воркера) після коміту публікується в Redis, а браузери отримують її через Server-Sent Events.
- **Без Redis теж працює:** задачі виконуються одразу в запиті, воркер переходить на простий цикл,
  а інтерфейс оновлюється раз на 30 с (зелена крапка біля назви компанії показує режим реального часу).
- **API захищене від CSRF:** зміни приймаються лише із заголовком `X-CRM: 1` і cookie сесії.

## Можливості

**Замовлення**
- Прийом заявок з лендингів через webhook (HTML-форма, JSON, PHP-проксі), UTM-мітки, IP, сайт.
- Пошук дублів за телефоном (налаштовуване вікно в днях), історія замовлень клієнта.
- Статуси з кольорами, порядком і дією зі складом; можна додавати власні.
- Товари в замовленні, апсели, знижка, передоплата, автоматичний розрахунок накладеного платежу.
- Розподіл заявок: вручну («Взяти собі») або по черзі між менеджерами.
- Масові дії: статус, менеджер, створення ТТН, оновлення трекінгу. Експорт у CSV.
- Захист від одночасного редагування одного замовлення двома менеджерами.
- Повна історія змін кожного замовлення.

**Склад і закупівлі**
- Залишок, резерв і доступна кількість по кожному товару, поріг «закінчується».
- Резерв при підтвердженні, списання при відправці, повернення на склад, зняття резерву при скасуванні.
  Кожна дія виконується рівно один раз, навіть якщо статус змінюють туди-сюди.
- Закупівлі в постачальників з оприбуткуванням і розрахунком середньої собівартості.
- Інвентаризація та журнал руху кожного товару.

**Доставка**
- Нова Пошта: пошук міст і відділень/поштоматів, створення та видалення ТТН, грошовий переказ або
  «контроль оплати», друк наклейки, трекінг.
- Укрпошта і Meest (бета): створення відправлень, наклейки, трекінг.
- Будь-яку ТТН можна вставити вручну — вона теж відстежуватиметься.
- Фоновий трекінг: «Відправлено» → «Отримано» / «Відмова» змінюються автоматично.

**Гроші**
- Очікуваний накладений платіж створюється при відправці, переходить у «Оплачено клієнтом»
  за трекінгом і в «Гроші отримано» після звірки.
- Імпорт CSV-реєстру від перевізника або банку з автоматичним визначенням колонок
  і звітом про розбіжності сум та невідомі ТТН.

**SMS / Viber** — TurboSMS, шаблони для кожного статусу зі змінними, черга з повторними спробами.

**Звіти** — заявки, апрув, середній чек, викуп, виручка і валовий прибуток у розрізі джерела,
кампанії, оголошення, сайту, менеджера та служби доставки; графік по днях; звіт по товарах і апселах.

**Ролі** — адміністратор, менеджер (може бачити лише свої замовлення), склад. Журнал дій усіх користувачів.

## Встановлення на VPS (Ubuntu 22.04/24.04)

Потрібно: VPS з 1–2 ГБ RAM і домен (наприклад `crm.vash-sait.com`) із записом A на IP сервера.

```bash
# 1. Docker
curl -fsSL https://get.docker.com | sh

# 2. Проєкт (завантажте архів на сервер, наприклад: scp crm.zip root@IP:~)
apt install -y unzip && unzip ~/crm.zip -d /opt && cd /opt/crm

# 3. Налаштування
cp .env.example .env
nano .env        # DOMAIN, DB_PASSWORD, SECRET_KEY, ADMIN_PASSWORD
# згенерувати секрети:  openssl rand -hex 32

# 4. Запуск
docker compose up -d --build
docker compose logs -f web   # дочекайтесь "Application startup complete"
```

Відкрийте `https://ваш-домен` і увійдіть під логіном і паролем з `.env`. HTTPS-сертифікат
отримується автоматично (Caddy + Let's Encrypt).

### Варіант без Docker: поруч з іншим сайтом (як на mdmy.me/crm)

Якщо на сервері вже є сайт під nginx, CRM можна поставити в підкаталог домену:

```bash
git clone https://github.com/maksymchukdmytro/crm.git /opt/crm-src
sudo bash /opt/crm-src/deploy/install.sh mdmy.me /crm /etc/nginx/sites-available/mdmy
```

Скрипт поставить PostgreSQL, Redis, Python-середовище, збере інтерфейс (потрібен Node.js 18+;
без нього відкриється класичний інтерфейс), запустить служби `crm-web` (127.0.0.1:8020) і `crm-worker`,
додасть у файл сайту рядок `include snippets/crm.conf;` і покаже пароль першого входу
(він також зберігається в `/etc/crm/initial-admin.txt`). Налаштування — `/etc/crm/crm.env`,
копії бази — `/var/backups/crm`. Повторний запуск оновлює код, базу не чіпає.
На mdmy.me це робить автоматично `deploy/crm.sh` репозиторію mdmy.me (таймер `crm-update`, кожні 5 хв).

### Перший запуск: що налаштувати

1. **Профіль** — змініть пароль адміністратора.
2. **Налаштування → Користувачі** — додайте менеджерів і склад.
3. **Товари** — додайте товари з артикулами (SKU), цінами, собівартістю, вагою і залишками.
4. **Налаштування → Доставка → Нова Пошта** — вставте API-ключ, збережіть, натисніть
   «Завантажити відправника», оберіть місто і відділення відправки, збережіть.
5. **Налаштування → Прийом заявок** — скопіюйте адресу з ключем у форми лендингів (є готові приклади).
6. **Налаштування → SMS** — токен TurboSMS, альфа-ім'я, тестове повідомлення, увімкніть автовідправку.
7. **Налаштування → Загальні** — розподіл заявок, вікно дублів, видимість замовлень менеджерам.

Перед роботою зробіть одне тестове замовлення від заявки до ТТН і перевірте його в кабінеті перевізника.

### Спробувати локально без домену

```bash
cp .env.example .env    # DOMAIN=localhost, HTTPS_ONLY=0, решта — будь-які значення
docker compose up -d --build db redis web worker
docker compose exec web python demo_data.py   # 140 демонстраційних замовлень (лише для тесту!)
```
Відкрийте http://127.0.0.1:8000.

## Моніторинг

| Що | Як увімкнути |
|---|---|
| **Сторінка «Система»** | Є одразу (адміністратор): стан бази, Redis, воркера, черги, трекінгу, SMS і заявок. |
| **Сповіщення в Telegram** | «Система» → токен бота й ID чату. Пише, коли не йдуть SMS, перевізник не відповідає 3 рази поспіль, черга переповнена або давно немає заявок (поріг у годинах, 8:00–22:00), і ще раз — коли відновилось. |
| **Зовнішній монітор** | Додайте `https://домен/crm/healthz/full` в UptimeRobot чи подібний сервіс: 503, якщо база, Redis або воркер не працюють. |
| **Sentry** (помилки) | `SENTRY_DSN=` (сервер і воркер) і `SENTRY_DSN_FRONTEND=` (браузер) у `/etc/crm/crm.env`, потім `systemctl restart crm-web crm-worker`. Телефони й імена клієнтів не надсилаються. |
| **Prometheus / Grafana** | `GET /crm/api/metrics` із заголовком `Authorization: Bearer <METRICS_TOKEN>` (токен створюється в `/etc/crm/crm.env`). Метрики: запити й час відповіді за маршрутами, стан компонентів, черга, заявки, SMS, помилки трекінгу. |

## Документація API

Схема OpenAPI — `/crm/api/openapi.json`, інтерактивна документація — `/crm/api/docs` (після входу).
Типи фронтенду генеруються з цієї схеми (`frontend/src/lib/api-schema.d.ts`); тест
`test_openapi_snapshot_is_current` падає, якщо API змінили, а типи — ні:
```bash
python scripts/export_openapi.py && (cd frontend && npm run gen:api)
```

## Обслуговування

| Що | Команда |
|---|---|
| Резервна копія | `./backup.sh` (у cron щодня: див. коментар у файлі) |
| Відновлення | `gunzip -c backups/файл.sql.gz \| docker compose exec -T db psql -U crm crm` |
| Оновлення коду | замініть файли і `docker compose up -d --build` (міграції БД застосовуються автоматично) |
| Логи | `docker compose logs -f web worker` |
| Перезапуск | `docker compose restart` |

Копіюйте резервні копії й за межі сервера (на інший сервер чи хмарний диск).

## Що варто знати

- **Укрпошта і Meest** написані за документацією й не перевірені на бойових акаунтах. Спершу зробіть
  тестове відправлення. Якщо API поверне помилку про поля, правки вносяться в один файл
  (`app/carriers/ukrposhta.py` чи `app/carriers/meest.py`). Для Укрпошти підтримується доставка
  «відділення → відділення» за індексом; для Meest ID відділення отримувача вводиться вручну.
- **Нова Пошта**: доставка на відділення та поштомати. Адресна доставка кур'єром НП поки не реалізована.
- Секрети (API-ключі) зберігаються в базі даних — обмежте доступ до сервера і регулярно робіть бекапи.
- Ключ webhook видно в коді сторінки, якщо форма шле запит напряму. Щоб його сховати, використовуйте
  PHP-проксі з прикладу в налаштуваннях. Ключ можна перевипустити будь-коли.

## Для розробника

```
app/
  models.py          таблиці БД
  services/          бізнес-логіка: orders, stock, payments, delivery, sms, reports,
                     events (події після коміту), queue (постановка задач), monitoring
                     (Sentry, метрики, пульс воркера, сповіщення)
  api/               JSON API: schemas (Pydantic-схеми запитів і відповідей), core (вхід, meta, SSE),
                     orders, catalog, admin (оплати, звіти, журнал, налаштування, стан системи)
  tasks.py           задачі воркера arq
  carriers/          інтеграції з перевізниками (спільний інтерфейс у base.py)
  routers/           класичний інтерфейс (/classic) і webhook прийому заявок
  templates/, static/  класичний інтерфейс (Jinja2)
frontend/            новий інтерфейс: React 19, Vite, TypeScript, TanStack Query/Virtual, dnd-kit
worker.py            запуск воркера (arq з Redis або простий цикл без нього)
migrations/          міграції Alembic
tests/               автотести (85 сценаріїв: бізнес-логіка, API, схема, черга, події, моніторинг)
deploy/install.sh    встановлення без Docker (підкаталог наявного сайту)
```

Стек: Python 3.12, FastAPI, SQLAlchemy 2, PostgreSQL 16, Redis 7 + arq, Alembic,
React 19 + TypeScript + Vite, Docker Compose, Caddy.

Розробка інтерфейсу:
```bash
uvicorn app.main:app --port 8077            # API (REDIS_URL=redis://localhost:6379/0 — для реального часу)
python worker.py                            # воркер
cd frontend && npm install && npm run dev   # http://localhost:5173, запити /api проксуються на 8077
npm run build                               # збірка в frontend/dist (її віддає FastAPI)
```

Запуск тестів (потрібен PostgreSQL з базою `crm_test`; тести черги й подій — ще й Redis на localhost):
```bash
pip install -r requirements.txt pytest
TEST_DATABASE_URL=postgresql+psycopg://user:pass@localhost/crm_test pytest
```

Зміна моделей: відредагуйте `app/models.py`, потім
`alembic revision --autogenerate -m "опис"` і перевірте згенерований файл у `migrations/versions/`.
