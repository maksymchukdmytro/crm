вагою, опис, післяплата. Розміри й опис відправлення в картці товару. Міграція `0004`.

## 🟡 Етап 5. Статистика (M)

**Що треба:**
- Графік статусів за днями, тип дати (створене / відправлене / змінене), готові періоди.
- Основне / допродаж: замовлення, товари, маржа, сума, %.
- Фільтри: джерело, вид оплати, додаткові поля, UTM, товар, менеджер.

**Що вже є в гілці `wip/etap-5-stats`** (коміт `5d953cd`, від `c9688c0`):
- `GET /api/stats` (`app/api/stats.py`): дні × статуси, частки статусів, підсумок основне / допродаж
  (кількість, сума, маржа, середній чек, % допродажу), таблиця товарів. Менеджер бачить лише свої
  замовлення (`visible_orders_query`). Знижка зменшує суму й маржу основного продажу.
- Сторінка `frontend/src/pages/Stats.tsx`: 10 готових періодів + свій, тип дати, фільтри статусу,
  товару, оплати, доставки, відділу, джерела, менеджера (для адміна), пошук по додаткових полях.
- Тест `test_stats_main_vs_upsell`, оновлені `openapi.json` і `api-schema.d.ts`.

**Що лишилось:**
1. Прогнати повний `pytest` і `npm run build` на гілці (ще не прогнано після останніх змін `main`).
2. У сторінці немає фільтрів UTM (`utm_source`), країни й сайту, хоча API їх приймає, — додати
   (вибір зі значень, що трапляються за період).
3. Перевірити на реальних даних, що цифри збігаються з LP-CRM за той самий період.
4. Злити в `main` (коміт «Етап 5: статистика»), дочекатися нової версії на `/crm/healthz`.

На майбутнє: зараз підрахунок іде в Python по всіх замовленнях періоду — нормально до десятків
тисяч; якщо стане повільно, перенести агрегацію в SQL (`GROUP BY`).

## ⬜ Етап 6. Товари й покупці (L)

**Що треба:**
- Картка товару: категорія, бренд, країна, фото, опис, знижка.
- Атрибути (варіанти) із залишками.
- Розділ «Покупці»: історія, сума, відмови, чорний список.

**Від чого відштовхуватись у коді:**
- `Product` зараз плаский: SKU, ціна, собівартість, вага, розміри, залишок / резерв, допродаж.
  Категорій, брендів, фото й варіантів немає.
- Варіанти найважча частина: склад (`services/stock.py`), резерв, закупівлі, позиції замовлень
  і імпорт з маркетплейсів зараз прив'язані до `product_id`. Пропозиція: окрема таблиця варіантів
  з власним SKU й залишком, а `OrderItem` / `PurchaseItem` / `StockMovement` отримують
  `variant_id` (товар без варіантів = один варіант за замовчуванням), з міграцією наявних залишків.
- Фото: зберігати файли на сервері (каталог поза `/opt/crm`, бо `install.sh` робить `rsync --delete`),
  віддавати через окремий маршрут.
- Покупців як окремої таблиці немає — історія зараз шукається за телефоном (дублі в
  `services/orders.py`). Пропозиція: таблиця `customers` (ключ — нормалізований телефон),
  `orders.customer_id`, міграція наявних замовлень; сума покупок, кількість відмов і невикупів,
  позначка «чорний список» з причиною — і попередження в картці замовлення та при прийомі заявки.

## ⬜ Етап 7. Зручність і розсилки (M)

**Що треба:**
- Фільтр під кожною колонкою списку, вибір колонок.
- Відправка: масове створення ТТН, реєстри, друк наклеєк пачкою.
- Розсилки SMS / Viber за фільтром, країна й оператор телефону.

**Від чого відштовхуватись у коді:**
- Масові дії вже є (`POST /api/orders/bulk`: статус, менеджер, ТТН у фоні, трекінг) — для
  масового створення ТТН лишається вибір ключа НП і зведення помилок по кожному замовленню.
- Реєстри НП (ScanSheet) і пакетний друк наклеєк ще не реалізовані — додати в
  `carriers/novaposhta.py` і окрему сторінку «Відправка».
- SMS / Viber через TurboSMS уже працюють для окремих замовлень і шаблонів статусів
  (`services/sms.py`, черга з повторами). Розсилка = вибірка за фільтром списку + шаблон +
  попередній підрахунок отримувачів і вартості, відправка через ту саму чергу.
- Оператор (Київстар / Vodafone / lifecell) — за кодом номера; країна — за префіксом.
- Список замовлень — `frontend/src/pages/Orders.tsx` (віртуалізована таблиця); вибір колонок
  зберігати в налаштуваннях користувача, фільтри колонок передавати в API списку.
